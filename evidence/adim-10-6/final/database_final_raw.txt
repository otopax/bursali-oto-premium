FINDING 3: Invalid Unique Constraint Query Pattern
SEVERITY: P1
FILE: src/app/api/erp/workorders/[id]/route.js
LINE: 54-57
EVIDENCE:
```javascript
const order = await prisma.workOrder.findUnique({
  where: { 
    id: id,
    tenantId: session.user.tenantId
  },
```
REMEDIATION: The `findUnique` method requires all parameters in the `where` clause to form a unique identifier. In `prisma/schema.prisma`, `tenantId` is NOT part of a unique index with `id` (e.g., `@@unique([id, tenantId])` is missing). This query may cause runtime or validation errors. Change `findUnique` to `findFirst` to enforce tenant isolation safely.

FINDING 4: Destructive Hard Cascade Delete with Soft Deletes
SEVERITY: P2
FILE: prisma/schema.prisma
LINE: 445, 482
EVIDENCE: 
`customer Customer @relation(fields: [customerId], references: [id], onDelete: Cascade)`
`vehicle CustomerVehicle @relation(fields: [vehicleId], references: [id], onDelete: Cascade)`
REMEDIATION: The `Customer`, `CustomerVehicle`, and `WorkOrder` models all contain a `deletedAt DateTime? // Faz 2.5: Soft Delete` field. Using DB-level `onDelete: Cascade` is highly risky in a soft-delete architecture. If a physical cleanup deletes a customer, it will silently physically delete all associated vehicles and work orders, destroying historical data and ERB records. Remove `onDelete: Cascade` or handle relational integrity carefully in application code.
